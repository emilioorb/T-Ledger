# Spec: T-Ledger como PWA

## Objetivo

Hoy T-Ledger se abre como una página en el navegador. Se quiere **instalarlo en el teléfono y en
la compu como una app**, con su ícono, en pantalla completa y sin la barra del navegador, y que
abra rápido porque la interfaz ya está guardada en el dispositivo.

Quien lo usa: cualquier persona con cuenta, sobre todo desde el teléfono, para anotar un gasto
en el momento.

## Comportamiento

- **Instalable.** Chrome y Edge (Android y escritorio) ofrecen «Instalar T-Ledger». En iPhone,
  «Agregar a pantalla de inicio» deja el ícono correcto y abre sin la barra de Safari.
- **Abre como app.** `display: standalone`, nombre «T-Ledger», ícono del logo (el mismo de
  `favicon.svg`), color del sistema según el tema claro u oscuro.
- **La interfaz queda guardada, los datos no.** El service worker guarda solo los archivos de la
  app (HTML, JS, CSS, fuentes, íconos). **Nada de `/api` se guarda**: las cifras del libro nunca
  quedan en el dispositivo, cada dato sale de la API como hoy. Así un teléfono compartido o
  perdido no expone el libro, y la sesión sigue siendo la cookie de siempre.
- **Sin conexión.** La app abre igual y muestra un aviso fijo «Sin conexión: los datos vuelven
  cuando vuelva la red». No se anota nada offline: no hay cola de cambios pendientes.
- **Versiones nuevas.** Cuando hay un deploy, la app avisa «Hay una versión nueva» con un botón
  «Actualizar». No se recarga sola: un formulario a medio llenar no se pierde.

## Fuera de alcance

- Anotar sin conexión y sincronizar después (implica cola, conflictos y datos en el dispositivo).
- Notificaciones push (van con el bot de Telegram).
- Publicarla en tiendas de apps.

## Stack

- Vite 8.3, React 19.2, TanStack Router 1.170.
- **Nuevas (dev):** `vite-plugin-pwa@1.3.0` (acepta `vite ^8`) y
  `@vite-pwa/assets-generator@1.0.4` (la 2.x choca con el peer `^1` del plugin) para sacar los íconos de `favicon.svg`.
  Fuente: https://vite-pwa-org.netlify.app/frameworks/react y
  https://vite-pwa-org.netlify.app/assets-generator/

## Decisiones técnicas

| Tema | Decisión | Por qué |
|---|---|---|
| Estrategia | `generateSW` (Workbox genera el SW) | No hace falta lógica propia en el SW |
| Actualización | `registerType: 'prompt'` + `useRegisterSW` | Recargar solo haría perder formularios |
| API | `navigateFallbackDenylist: [/^\/api\//]` y sin `runtimeCaching` | Que el SW no toque ni guarde la API |
| Íconos | preset `minimal-2023`: 64, 192, 512, maskable 512, apple 180 | El preset que recomienda la doc |
| Aviso de versión | toast de `sonner` (ya está en el proyecto) | Sin componentes nuevos |
| Sin conexión | eventos `online`/`offline` del navegador | No depende del SW |
| Vercel | `Cache-Control: no-cache` para `/sw.js` y el manifest | Que el navegador detecte cada deploy |

## Comandos

```
Dev:      npm run dev            (en web/)
Tests:    npm test
Tipos:    npm run typecheck
Build:    npm run build
Preview:  npm run preview        (el SW solo se registra en build)
Medición: npx lighthouse <url> --output json   (antes y después)
```

## Estructura

```
web/vite.config.ts                    → VitePWA(...)
web/pwa-assets.config.ts              → preset de íconos desde public/favicon.svg
web/public/                           → íconos generados (se commitean)
web/index.html                        → theme-color por tema, apple-touch-icon
web/src/features/pwa/                 → aviso de versión y aviso sin conexión, con sus tests
web/vercel.json                       → headers de no-cache para sw.js y manifest
```

## Pruebas

- **Unitarias (Vitest + Testing Library):** el aviso de sin conexión aparece con el evento
  `offline` y se va con `online`. El aviso de versión llama a `updateServiceWorker(true)` al
  tocar «Actualizar» (el módulo virtual se reemplaza en el test).
- **Build:** `dist/` trae `sw.js` y `manifest.webmanifest`, y el precache del SW no incluye
  nada bajo `/api`.
- **Navegador (Chrome DevTools):** en Application, el manifest sin errores y el SW activo.
  En Network, las llamadas a `/api` salen a la red y no del SW. Offline: la app abre y muestra
  el aviso.
- **Lighthouse** antes y después, contra producción.
- **Real:** instalarla en Android y en iPhone.

## Límites

- **Siempre:** la API pasa por la red. Los tests y el build en verde antes de cada commit.
  Medir antes y después.
- **Preguntar antes:** guardar cualquier dato de la API en el dispositivo o agregar sync offline.
- **Nunca:** cachear respuestas autenticadas. Recargar la app sin que la persona lo pida.

## Criterios de éxito

1. Lighthouse en producción: la app es instalable (manifest válido, SW activo, íconos 192 y 512
   con maskable).
2. En Network de DevTools, ninguna respuesta de `/api` sale del service worker.
3. Offline, la app abre en menos de 1 s desde el caché y muestra el aviso de sin conexión.
4. Después de un deploy, la app abierta muestra «Hay una versión nueva» y actualiza al tocar.
5. La performance de Lighthouse no baja respecto de la medición previa.
6. Instalada en Android y en iPhone, abre sin la barra del navegador y con el ícono correcto.

## Preguntas abiertas

- Ninguna bloqueante. Por defecto el color de la barra del sistema sigue el tema claro u oscuro
  del sistema operativo, no el que se elige dentro de la app.
